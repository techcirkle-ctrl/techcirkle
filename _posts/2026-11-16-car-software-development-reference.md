## 1. Software domains

| Domain | What it does | Typical tech | Safety posture |
|---|---|---|---|
| Embedded and real-time | Engine, battery, motor, braking, steering, body control | C or C++, AUTOSAR-style stacks | Highest rigour |
| ADAS and autonomy | Perception, sensor fusion, planning, driver monitoring | Embedded code plus ML models | High |
| Infotainment and cockpit | Navigation, media, voice, digital cluster | Android Automotive, QNX, Linux | Mixed |
| Connected services | Telematics, remote commands, OTA, fleet analytics | Cloud services | Non-safety-critical, security-critical |
| Companion apps | Remote lock, climate, charging, service booking | Mobile | Non-safety-critical |
| Retail and aftersales | Configurators, dealer systems, warranty, parts | Enterprise web | Non-safety-critical |

Rule of thumb: never plan these as one workstream.

## 2. Standards and regulations

| Standard | Covers | Why it matters |
|---|---|---|
| ISO 26262 | Functional safety, ASIL A to D | Sets rigour for design, verification and tools |
| ISO/SAE 21434 | Cybersecurity engineering | Threat analysis and risk assessment per interface |
| UNECE R155 | Cybersecurity management systems | Organisational security process |
| UNECE R156 | Software update management | Governs the OTA pipeline |
| Automotive SPICE | Process maturity | Assesses how you develop |
| GDPR and local rules | Personal and telematics data | Consent, retention, anonymisation |

Practical consequences: requirement traceability from need to test evidence, qualified toolchains, independent verification at higher ASIL levels, and a documented vulnerability response process.

**Action:** classify the safety level of every component in week one.

## 3. Platform options

| Platform | Strengths | Trade-offs |
|---|---|---|
| Android Automotive | Large ecosystem, familiar tools | Ties you to a vendor roadmap |
| QNX and similar real-time platforms | Certified foundations for safety work | Narrower ecosystem |
| Embedded Linux and open-source stacks | Control and flexibility | More integration effort |

To limit lock-in: add an abstraction layer between applications and platform services, keep business logic portable, own the vehicle-to-cloud data contracts and negotiate long-term support commitments.

## 4. Cost ranges

First production release, rough planning figures:

| Scope | Range |
|---|---|
| Companion app plus connected backend | 150,000 to 600,000 USD |
| Cockpit or infotainment application layer on an existing platform | 300,000 to 1.5 million USD |
| OTA platform with signing, staged rollout and traceability | 400,000 to 1.2 million USD |
| ADAS and safety-critical functions | Multi-million, long certification |

Maintenance: budget 15 to 25 percent of build cost per year, more for connected features. Typical first release of an app with backend: four to nine months.

## 5. Testing layers

1. **Unit and component tests** on every commit.
2. **Software-in-the-loop** simulation of full functions against modelled vehicles.
3. **Hardware-in-the-loop** benches for timing and electrical behaviour.
4. **Vehicle and fleet testing** for real-world conditions.

Push testing left into virtual environments. Virtual ECUs and cloud-scaled simulation let teams run thousands of cases overnight.

### Traceability checklist

- [ ] Each requirement links to a design element, an implementation and a test result.
- [ ] Each release links to the requirement baseline and tool versions.
- [ ] Each field issue links back to the requirement or test gap.
- [ ] Reports are generated by the toolchain, not assembled by hand.

## 6. Design rules for connected services

- Version every API and telemetry schema from day one.
- Treat the vehicle as untrusted and enforce authorisation server-side.
- Design for offline operation: commands queue, expire and confirm.
- Separate operational data from personal data.
- Build an entitlement model early if you plan paid features.

For platform detail, see our guide to [cloud application development](https://techcirkle.com/blog/cloud-application-development-guide).

## 7. Twelve-month checklist

| Months | Focus |
|---|---|
| 1 to 2 | Discovery, safety classification, architecture options, threat analysis, build-versus-buy |
| 2 to 4 | Vertical slice from simulator to cloud to app; CI and simulation foundation |
| 4 to 8 | Scale team, core services, first real vehicle variant, first external security assessment |
| 8 to 12 | Pilot fleet, OTA rollout rehearsal, runbooks, data-driven backlog |

Governance: one architecture authority, interface contracts in a shared repository, a standing forum for breaking changes.

## 8. Common pitfalls

- Architecture diagrams with no vertical slice.
- Cybersecurity treated as a pre-launch checklist.
- Too little investment in simulation.
- Ignoring fleet heterogeneity.
- Underestimating long-term support.
- Overpromising AI features without validation and fallback plans.

## Frequently Asked Questions

### What is the difference between ISO 26262 and ISO/SAE 21434?

ISO 26262 addresses functional safety, meaning hazards from malfunctioning electronics. ISO/SAE 21434 addresses cybersecurity engineering, meaning protection against malicious attack. Most connected functions must satisfy both.

### Which layer should a non-automotive team start with?

Usually the connected layer or a companion app, because they follow familiar cloud and mobile patterns and are non-safety-critical.

### How should AI be used in this domain?

Inside the product for voice assistants, predictive maintenance and service workflows, and inside engineering for test generation and log triage. Human review stays on safety arguments.

### What makes OTA different from a normal deployment?

Signed packages, compatibility checks across hardware revisions, staged rollout, rollback and regulatory traceability for each change.
